06Why it survives

  1. Worker dies mid-runClaim rides a 5s lease; the ticket never left the queue. Any peer re-claims within seconds.
  2. Leader diesLease-backed leader key evaporates; followers re-elect atomically within the session TTL.
  3. Double enqueuePut-if-not-exists on the ticket key makes redelivery a no-op. At-most-once enqueue.
  4. Missed firesPer-job watermark plus catch-up policy replays the gap: latest, all, or skip.
  5. Zombie leaderA partitioned ex-leader cannot commit anything. Split-brain is impossible by lease fencing.
  6. Slow workerCompletion re-verifies claim ownership, so a replacement run is never corrupted.

Chaos test, live

Start the three-node demo, schedule the heartbeat, then kill things and watch the ledger keep moving.

docker compose -f deploy/docker-compose.yml up -d --build
curl -X POST localhost:8081/api/jobs -H "content-type: application/json" -d "{\"name\":\"heartbeat\",\"cron\":\"*/5 * * * * *\",\"command\":\"sleep 8 && echo alive\",\"max_retries\":3}
docker compose kill node2    # worker dies mid-run -> attempt+1 elsewhere
docker compose kill node1    # leader dies -> re-election, schedule resumes

Delivery is at-least-once: a run may execute twice only if a worker dies after finishing but before reporting. Enqueue itself is at-most-once. The industry-standard trade-off.
